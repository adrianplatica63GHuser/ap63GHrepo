# Docker image, Ciprian UAT delivery & env vars

<!-- Extracted verbatim from CLAUDE.md (Slice 24.01.optimization). Original line numbers in brackets. -->

- **Ciprian UAT schema + reference-data delivery (UC-C6, `GA40.Operations.Guide.05.docx`).** Every DB schema change is delivered to Ciprian as a single fixed-name file, `ciprian-schema-update.sql`, at the root of `C:\dev\ga40prj.Ciprian\`. It is **fully regenerated, never hand-edited**, every time `build-ciprian-image.ps1` runs (Step 5), assembled live from `ga40prj-postgres`: (1) `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`; (2) Ciprian's `01-extensions.sql`; (3) `pg_dump --schema-only`; (4) `pg_dump --data-only -t 'lookup_*'`. Applying it **wipes Ciprian's entire UAT database** and rebuilds it to match dev (acceptable while Ciprian's data is disposable). **`build-ciprian-image.ps1` runs a pre-flight check (Step 0.5) before any dump: it queries `schema_migrations` in `ga40prj-postgres` and aborts if any `migration_*.sql` file in `src/db/` is unapplied — generating the schema from an incomplete DB would silently corrupt Ciprian's instance. Always run `scripts\Apply-Migration.ps1` first.** **Adrian never runs commands against `ciprian-ga40prj-postgres` himself** — that container is on Ciprian's PC; delivery always goes through the Ops Guide: schema/refdata change → **UC-C6** (send `ga40prj-app.tar` + `ciprian-schema-update.sql`); code-only → **UC-C5** (app tar only); full reset with no new version → **UC-C8**. `src/db/sync-reference-data.sql` / `npm run export:reference-data` are no longer part of the Ciprian flow. **Upcoming transition — data-preservation mode:** once Ciprian starts keeping real data (imminent), the full-wipe delivery will be replaced by a delta approach: identify which `migration_*.sql` files Ciprian has NOT yet applied (by querying his `schema_migrations` table), send only those, and apply them in order without touching his data. The pre-flight check already provides the foundation. A future slice will implement `ciprian-send-migrations.ps1` (or equivalent). Until then, the full-wipe flow remains in place.

- **Never put `--ignore-scripts` on the Dockerfile's `npm ci`, and never downgrade it to `npm install`.** `public/pdf.worker.min.js` is **gitignored** and exists only because the `postinstall` script (`scripts/copy-pdfjs-worker.mjs`) copies it out of `node_modules`. `--ignore-scripts` skips postinstall, so the file is never generated in the image; the builder's `COPY . .` then finds nothing to copy, because `.dockerignore` does not exclude `public/` but the file simply isn't there on a clean checkout. The result is a runtime 404 on `/pdf.worker.min.js` and broken PDF rasterisation in Admin → Import — **and only on a clean build**, so on a dev machine where postinstall has run at least once it looks like it works and the failure appears intermittent. `npm install` is separately wrong because it can rewrite the lockfile, so the image stops matching what CI built. Vercel is unaffected (it runs its own install with scripts enabled); this bites the Docker/Ciprian path only. Hit while landing Slice #19.28.e2e, where it had been applied as a workaround. Note the workaround was also unnecessary: no playwright package declares an install script (`hasInstallScript=false` in `package-lock.json`), so `npm ci` never tries to download browsers into the image.

- **`.dockerignore` does NOT inherit `.gitignore`.** They are independent files with independent rules. `e2e/.auth/session.json` holds a live Supabase session cookie and is gitignored — but until Slice #19.28.e2e added an explicit `e2e` entry to `.dockerignore`, it was still shipped into the Docker build context and baked into the builder layer. Whenever a new gitignored path holds a secret, add it to BOTH files.

- **Docker Compose `--env-file` does NOT inject every `.env` variable into a container.** It only makes values available for `${VAR}` substitution *inside the compose YAML*. A variable must be explicitly listed in the service's own `environment:` block (as `KEY: ${KEY}` or a literal) to be readable as `process.env.X` in the container. **When adding a new env var the app reads, also add it to the `environment:` block of every `docker-compose.yml` that runs the app** — local dev's and Ciprian's are separate files.

- **Ciprian's UAT container runs with `NODE_ENV=production` but no real Supabase project.** Code that branches purely on `NODE_ENV === "production"` to use a cloud backend will fail there. Document-page storage has an override: `LOCAL_FILE_STORAGE=true` forces the local-filesystem path even in production. If a future feature adds a "real backend required" path, check whether it needs a similar override rather than trusting `NODE_ENV` alone.
