# Docker image, Ciprian UAT delivery & env vars

<!-- Extracted verbatim from CLAUDE.md (Slice 24.01.optimization). Original line numbers in brackets. -->

- **Ciprian UAT schema + reference-data delivery (UC-C6, `GA40.Operations.Guide.05.docx`).** Every DB schema change is delivered to Ciprian as a single fixed-name file, `ciprian-schema-update.sql`, at the root of `C:\dev\ga40prj.Ciprian\`. It is **fully regenerated, never hand-edited**, every time `build-ciprian-image.ps1` runs (Step 5), assembled live from `ga40prj-postgres`. ⚠️ **Nothing in Ciprian's folder is touched until the script's Step 6 verification passes** — every file that replaces one of his is written as a sibling `.new` and renamed into place by Step 7, so a failed build leaves the last good package intact rather than half-replaced. Contents: (1) `DROP SCHEMA public CASCADE; CREATE SCHEMA public;`; (2) Ciprian's `01-extensions.sql`; (3) `pg_dump --schema-only`; (4) a `pg_dump --data-only` of **every reference table**. ⚠️ **That set is `$refTablePatterns` in the script, not `lookup_*`** — the prefix is a naming convention, not the definition, and three reference tables do not carry it (`time_frame_setting`, `help_content`, `help_hint`). The test for membership is *does Ciprian's build read this table at runtime*, NOT *is its admin screen in his nav*: the help and settings EDITORS are `devOnly` and absent from his build, while the help READER is mounted on every screen by `breadcrumb-bar.tsx` and the time-frame values drive his dashboard counters and expiry badges. Both tables failed the wrong test for months and shipped empty, silently, because both readers fall back rather than erroring. Step 6 of the script now verifies the package against dev and lists any populated table it classifies as neither reference nor operational. Applying it **wipes Ciprian's entire UAT database** and rebuilds it to match dev (acceptable while Ciprian's data is disposable). **`build-ciprian-image.ps1` runs a pre-flight check (Step 0.5) before any dump: it queries `schema_migrations` in `ga40prj-postgres` and aborts if any `migration_*.sql` file in `src/db/` is unapplied — generating the schema from an incomplete DB would silently corrupt Ciprian's instance. Always run `scripts\Apply-Migration.ps1` first.** **Adrian never runs commands against `ciprian-ga40prj-postgres` himself** — that container is on Ciprian's PC; delivery always goes through the Ops Guide: schema/refdata change → **UC-C6** (send `ga40prj-app.tar` + `ciprian-schema-update.sql` + `ciprian-init.zip`); code-only → **UC-C5** (app tar only); full reset with no new version → **UC-C8**.

- **`ciprian-init.zip` is the third deliverable, and it exists because the first two never reached the init folder.** `C:\dev\ga40prj.Ciprian\docker\postgres\init\` is bind-mounted at `/docker-entrypoint-initdb.d` and is what a **first-time setup** and a **full reset (UC-C8, `compose down -v`)** rebuild the database from. `build-ciprian-image.ps1` has regenerated `02-schema.sql` there on every build since it was written — but only in ADRIAN's copy of that folder, and the handover named two files. So Ciprian's own init folder was still the one he was given on day one, and his `03-reference-data.sql` had additionally rotted into a file that aborts the boot outright (it truncates `lookup_others`, dropped by migration_052, and inserts document types without the `key` that migration_071 made NOT NULL). Step 5.5 now regenerates that file from the same live dump as section 4 of the update file, and Step 7 zips the three init `.sql` files, plus a generated `README-INIT.txt` telling Ciprian what the folder is and to unpack the zip every time, for delivery. **Send it every time; he only needs it on the day he resets, and that is exactly the day it is too late to ask for.**

- **Never put `--ignore-scripts` on the Dockerfile's `npm ci`, and never downgrade it to `npm install`.** `public/pdf.worker.min.js` is **gitignored** and exists only because the `postinstall` script (`scripts/copy-pdfjs-worker.mjs`) copies it out of `node_modules`. `--ignore-scripts` skips postinstall, and the file is gitignored, so on a clean checkout the builder's `COPY . .` finds nothing to copy. The result is a runtime 404 on `/pdf.worker.min.js` and broken PDF rasterisation in Admin → Import — **and only on a clean build**, so on a dev machine where postinstall has run at least once it looks like it works and the failure appears intermittent.

- **Two corrections to the bullet above, both measured when a cold `docker build` finally failed on 27 Aug.** (1) **The `deps` stage's postinstall never put that file in the image** — it writes into that stage's own `/app/public`, and the builder copies only `node_modules` across, so its output was always discarded; the file reached the image solely from whatever happened to be in Adrian's working tree. The builder now runs `node scripts/copy-pdfjs-worker.mjs` explicitly after `COPY . .`, which is what actually makes a clean checkout safe. (2) **`npm ci` in the `deps` stage could not run at all**, because that stage copies only `package.json`/`package-lock.json` and npm runs `postinstall` from `/app`: `Cannot find module '/app/scripts/copy-pdfjs-worker.mjs'`, exit 1. It had been broken since `8b817ff` (2 Jul), which added both the script and the `postinstall` entry to a deps stage that has only ever copied `package*.json`, and was hidden for nearly two months by the layer cache — **a cached `RUN` proves nothing about whether it works**, and the first fresh `node:22-alpine` digest is what re-ran it. The stage now copies that one script (not the whole folder, which would invalidate the install layer on every unrelated script edit). (3) **The reason to keep install scripts on is not the worker at all** — it is that `sharp`, `esbuild`, `@swc/core`, `unrs-resolver`, `tesseract.js` and `@parcel/watcher` place their native binaries from install scripts. Do not read correction (1) as making `--ignore-scripts` safe. `npm install` is separately wrong because it can rewrite the lockfile, so the image stops matching what CI built. Vercel is unaffected (it runs its own install with scripts enabled); this bites the Docker/Ciprian path only. Hit while landing Slice #19.28.e2e, where it had been applied as a workaround. Note the workaround was also unnecessary: no playwright package declares an install script (`hasInstallScript=false` in `package-lock.json`), so `npm ci` never tries to download browsers into the image.

- **`.dockerignore` does NOT inherit `.gitignore`.** They are independent files with independent rules. `e2e/.auth/session.json` holds a live Supabase session cookie and is gitignored — but until Slice #19.28.e2e added an explicit `e2e` entry to `.dockerignore`, it was still shipped into the Docker build context and baked into the builder layer. Whenever a new gitignored path holds a secret, add it to BOTH files.

- **Docker Compose `--env-file` does NOT inject every `.env` variable into a container.** It only makes values available for `${VAR}` substitution *inside the compose YAML*. A variable must be explicitly listed in the service's own `environment:` block (as `KEY: ${KEY}` or a literal) to be readable as `process.env.X` in the container. **When adding a new env var the app reads, also add it to the `environment:` block of every `docker-compose.yml` that runs the app** — local dev's and Ciprian's are separate files.

- **Ciprian's UAT container runs with `NODE_ENV=production` but no real Supabase project.** Code that branches purely on `NODE_ENV === "production"` to use a cloud backend will fail there. Document-page storage has an override: `LOCAL_FILE_STORAGE=true` forces the local-filesystem path even in production. If a future feature adds a "real backend required" path, check whether it needs a similar override rather than trusting `NODE_ENV` alone.
