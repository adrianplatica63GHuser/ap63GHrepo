# Import wizard, provenance & inference

<!-- Extracted verbatim from CLAUDE.md (Slice 24.01.optimization). Original line numbers in brackets. -->

- **A key in `KNOWN_TYPE_KEYS` with no seeded `lookup_document_type` row is a silent trap.** `src/lib/import/classify-prompts.ts` offers that array to Haiku as the valid classification vocabulary, and `scan-folder`/`ai-interpret` whitelist the model's answer against it — but the resolver then looks the key up in the DB's own list. An unseeded key passes the whitelist and matches no stored row — and what happens next changed in Slice #29.07: until then it fell through to auto-creating a type from the free-text LABEL, so the document landed under a *generated* key (`CARTE_DE_IDENTITATE` where `CARTE_IDENTITATE` was meant); since #29.07 the resolver offers the canonical key itself, so the row is created under the key the model named. (Slice #29.06 replaced `ensureDocType`'s `typeMap` index with `matchDocumentType` over the rows themselves; the trap is unchanged, and so is its fix.) Anything matching on a literal key (e.g. `getPersonIdCardLink`, which looks for `CARTE_IDENTITATE`) then never finds it, and nothing errors. Found in Slice #23.01.Import, where six entries had drifted — one unseeded (`CARTE_IDENTITATE_ALT`) and five belonging to a different table entirely (`lookup_property_type`). **When adding a key to that array, add the migration in the same commit**, and cross-check with: `SELECT key FROM lookup_document_type ORDER BY key;` against the array. **This bullet used to end by saying an unseeded key could never come back through the auto-creation path — that a defensive match against such a key was "a lookalike sitting in a list of real things". Slice #29.07 made that false and the sentence has been removed.** `resolveClassifiedDocumentType` offers `canonicalTypeKey(answer.typeKey)` to `createDocumentTypeRow` as a preferred key, and `createDocumentTypeRow` refuses to substitute a suffixed one, so a whitelisted key lands on a row under exactly that key. Two things follow. The array and the seed must now agree in BOTH directions — `src/__tests__/document-type-catalogue-single-source.test.ts` enforces that against `src/db/sync-reference-data.sql`, so the manual cross-check above is a belt on top of a brace rather than the only guard. And a defensive match against a key nothing seeds is no longer provably dead code, so deleting one needs the argument made again rather than quoted from here. Note also that `migration_021`'s three genuine alternate wordings used to end in `_ALT` — the naming pattern is what made the phantom look legitimate, so match against the seed list, not against the suffix. **That advice is now the only thing that works: `migration_071_doctype_rekey.sql` retired the suffix entirely.** `AUTORIZATIE_ALT` became `AUTORIZATIE` (the key migration_043 had freed by deleting `Autorizare`), `CERTIFICAT_SARCINI` moved to `CERTIFICAT_BUNURI` so `CERTIFICAT_SARCINI_ALT` could take `CERTIFICAT_SARCINI`, and `EXTRAS_CARTE_FUNCIARA_ALT` was folded into `EXTRAS_CARTE_FUNCIARA` and deleted. No key in the catalogue ends in `_ALT`, so a search for the suffix returns nothing and proves nothing. ⚠️ `CERTIFICAT_SARCINI` is the one key in this codebase that has MEANT TWO DIFFERENT THINGS — `Certificat de Bunuri` before migration_071 and `Certificat de Sarcini` after — so a query, a fixture or a comment written against the old meaning is wrong in a way that reads as correct.

- **Import auto-creates document types from an AI label, with no confirmation — through ONE writer since Slice #29.06.** `resolveClassifiedDocumentType` (`src/lib/documents/resolve-document-type.ts`) is the only path from a classifier's answer to a `lookup_document_type` row: the wizard reaches it over `POST /api/document-types/resolve`, `ai-interpret` calls it in-process, and it is the only place that writes `origin: 'IMPORT'`. It matches key-then-name through `matchDocumentType`, adopts a concurrent create's row on 23505 rather than failing, and never invents a type from a label that normalises to nothing. Importing a folder of unfamiliar documents can still mint one row per distinct label the model produces — a genuinely different WORDING ("Contract de arendă" vs "Contract de arendare") is still a separate type, deliberately, because the archive holds three such pairs on purpose. What is no longer true, and was until #29.06: two independent creators (`ensureDocType` and `ai-interpret`) disagreeing about when two names are one name, a module-level `autoCreatedTypeCache` that outlived the run, and a failed create that filed the document under the catch-all in silence. **The gate that stops an import inventing a type at all is 29.08 and is still owed.** Discover mode never does this. Check for drift with: `SELECT key, name, origin, created_at FROM lookup_document_type ORDER BY created_at DESC;` — `origin = 'IMPORT'` is now the reliable marker, and rows created long after the seeding migrations are the auto-created ones.

- **Before editing any file under `src/app/**/_components/`, grep for an import of it.** One `grep -rn "<filename>" src` answers it in a second, and "the folder is named after the screen" is not evidence — `/admin/complex-query/page.tsx` is a three-line `redirect()` and its sibling `_components/` folder looked exactly like a live screen's. Unreachable files still lint and still type-check, because nothing runs them, so they drift for months without a single failure. This bites hardest under `src/app/admin/import/`, where the wrapper is still called `import-browser-dynamic.tsx` after a component that no longer exists and `/admin/import` renders **ImportWizard** as the only mounted entry point in the folder. Confirm a user can actually reach a file before spending a slice fixing it — and when a file turns out to be dead, delete it rather than gating it behind `<DevOnly>`, which implies it is live.

- **A cadastral value must be shown and editable before it is written.** `parseFolderName` may PRE-FILL visible, editable, Romanian-labelled tarla/parcela inputs that the user confirms before the Property is created — that is what `PropertyStepDialog`'s create-new branch does, through the pure `cadastralSuggestionFromFolderName` in `src/lib/import/coordinate-file.ts`, which is stricter than the raw parser in requiring the full `<tarla>-<parcela>` shape. What the import wizard must never do is infer a cadastral value silently: the bare heuristic false-positives on ordinary names ("3 Calea Victoriei" → tarla "3"; "2024-Arhiva" → tarla "2024", parcela "Arhiva"). If you find `parseFolderName` imported under `src/app/admin/import/` or `src/lib/import/`, check whether the value reaches the user before it is saved rather than reaching for a revert.

  Two callers outside the wizard still infer silently and were left that way deliberately: `src/app/api/documents/[id]/process/route.ts` (steps 5–6, the *Process* panel, which also calls `findEntitiesByTag` and so can associate every Document and Person sharing a tag string, not just this import's), and `addEntityTag` in `src/lib/metadata/queries.ts`, which auto-generates `"47/2"`-style alias tags. Treat a Process-panel report of a wrong tarla/parcela or an unexpected association as that known gap, not a regression. `tag-dialog.tsx` previews those alias tags on purpose — do not remove the preview while the server still creates them, or the dialog lies about what it is about to do.

- **A display value must never double as a lock.** Whatever is shown to a user will eventually be written by something that only owes you the display contract. `provenance` was honest metadata to `classifyFileSource` (`src/lib/metadata/provenance-rules.ts`, which maps by extension only and *deliberately never returns* `COORDINATE_FILE`, because a `.txt` is indistinguishable from any other text file by name alone) and a mutex to the Process route, and neither was wrong on its own terms — the result was a silently duplicated Property. A lock needs its own row: `property_corner_source` with `UNIQUE(document_id)` is the lock now, and provenance is metadata again.

## Harvested from the slice log

- **Write-if-empty, on every target a machine reading touches. Nothing a human typed is ever overwritten by a machine reading.** Read the current values first (a GET appends nothing), write only the nulls. This makes a second click, or a re-read against a document someone has since filled in, non-destructive for free. Treat a failed READ as a failed write — never as "every field is blank", which would invite exactly the overwrite the rule forbids.

- **Resolving a person from an extraction goes through the confirm-or-create ladder — never an unconditional `POST /api/people`.** The order is: exact `findNaturalPersonByCnp` → fuzzy `searchPersonsAll`, its results labelled **unconfirmed** → an explicit user decision of confirm / pick / create-new / skip. The fuzzy step tries the full name and then falls back to **surname alone**, because `person.displayName` is `"firstName lastName"` and `searchPersonsAll` is a single `ILIKE %pattern%`, so a middle name or a surname-first record misses entirely — and a missed suggestion is how a duplicate gets created. Use the shared `src/components/persons/person-resolution-dialog.tsx`; do not copy its branches into a new caller. `isCreateBranch()` is exported so a caller can render its review form under precisely the branch the dialog renders.

- **A metadata or provenance write is best-effort and must NEVER turn a successful create into an error response.** The entity row is already committed by the time `setInitialProvenance` runs, so a metadata failure that propagates would report failure for work that succeeded — or, worse, delete a correctly-created entity in a compensating action. Provenance stays outside any transaction, and its stamp goes last.

- **`src/lib/metadata/provenance.ts` is the single source of truth for provenance codes.** Never hardcode a copy of the value list in a filter dropdown or a statement map — three hardcoded copies had already drifted to values (`SCAN_OCR`, `MANUAL_ENTRY`, `EXTERNAL_DB`, `OTHER`) that were never storable, so two filters could not match a single row. Derive UI lists from the shared list so a new code cannot ship without its explanatory sentence.

- **Provenance rules (`src/lib/metadata/provenance-rules.ts`) key on the SOURCE alone, never on target × source.** The source is what determines provenance, and keying on it alone avoids combinatorial cases that all collapse to the same answer. **`unknown → null` means ASK THE USER** — `inferProvenanceForFiles` returns null for a mixed or unrecognised selection rather than picking a winner, and the UI must show a required select rather than guessing.

- **`property_corner_source` is the lock, and the `UNIQUE(document_id)` index IS the lock.** Claim with `INSERT … ON CONFLICT (document_id) DO NOTHING … RETURNING`; zero rows back means someone else already claimed it → 409. Never re-introduce a check-then-claim window, and never overload provenance (or any other display value) as a mutex again.

- **Claim the link BEFORE you PATCH the corners.** The link is the permission to write that geometry, so recording it afterwards would let a file belonging to another Property overwrite this one's corners first. Where the claim genuinely cannot happen up front — the bulk loop resolves the Property while the coordinate file is still a file handle with no `document` row to point at — take it the instant that file's Document is created, before its pages, its property link and its tags. Key the claim on whether corners were actually **written**, not on whether a file was picked: a file that was parsed and discarded did not build this Property and must stay free to build another.

- **`softDeleteProperty` must hard-delete the `property_corner_source` row.** Properties soft-delete, so the table's `ON DELETE CASCADE` never fires on the normal path and a stale link would block its source document forever. The link carries no history worth keeping.

- **`UNIQUE(document_id)` means re-pointing a link is impossible — it is not an `UPDATE`.** The recovery route is: soft-delete the wrong Property, which frees the document, then re-run the correct path. This constraint is deliberate; a request to move a link is a change of mind, not an oversight.

- **A coordinate file's NAME is a ranking signal and a warning, never a filter.** `coordinateNameConfidence(name)` returns `"strong"` (shortlisted extension **and** the name folds to a `coord` prefix) / `"weak"` (extension only) / `"none"`. `COORDINATE_FILE_EXTS` and `coordinateCandidates` stay untouched — only the parse decides usability, so a correctly-formed export with an unconventional name still imports. Exactly one `strong` candidate is pre-selected; two or more `strong` is a tie the name cannot break, so the user chooses, and every candidate stays visible and selectable either way. When the single candidate is only `weak`, show a quiet note (`role="status"`, small amber text, no banner) that blocks nothing. Derive the note from `candidates` at render time — never copy it into state, or there is a second copy to drift.

- **Apply `perToSlash` before writing `tarla` / `parcela`.** The Process route has always applied it, so suggesting a raw `"47per2"` would leave two Properties whose cadastral identifiers differ only in encoding.

- **Discover mode persists NOTHING and is safe to re-run on any document, any number of times.** No field mapping, no `customFields`, no `documentTypeId` resolution (so unlike the extract path it never auto-creates a `lookup_document_type` row), no party extraction, no `ai_interpreted_at` stamp. Do not gate its button on `aiInterpretedAt` — re-running after adding template fields to see what is still unrecognised is a primary use case.

- **`parseDiscoverPayload` never throws** — same contract as `parseTemplateFields`. A diagnostic that crashes on odd data fails exactly when the data is odd.

- **A page that cannot be sent to the model becomes a `skippedPages` entry with a per-page reason, and is reported** (including on the 422). Dropping it silently makes "the model found nothing" and "the model never saw this page" indistinguishable from outside; call the `application/octet-stream` case out by name — the file is fine, only its recorded MIME is missing.

- **`stop_reason === "max_tokens"` is surfaced as a loud TRUNCATED warning.** A silently partial read is the worst possible failure for a mode whose entire promise is completeness.

- **Cap results PER TYPE, never across types.** Four independent caps (DOC / JPERS / PPERS / PROP), with natural and judicial persons split rather than sharing a person budget — a shared budget lets one type crowd out another, which is the same defect one level down. Detect truncation with **limit + 1** (fetch 51, keep 50) and report it **per type**, so the notice names what is missing instead of saying "showing the first N results", which is true and useless.

- **Interleave the merged result set round-robin — one row per type per round, each type still ordered by code internally, types dropping out of the rotation as they run dry.** A plain code sort is why type-prefixed codes (`DOC` < `JPERS` < `PPERS` < `PROP`) put three pages of documents ahead of the first person.
