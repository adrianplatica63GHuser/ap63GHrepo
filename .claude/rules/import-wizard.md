# Import wizard, provenance & inference

<!-- Extracted verbatim from CLAUDE.md (Slice 24.01.optimization). Original line numbers in brackets. -->

- **A key in `KNOWN_TYPE_KEYS` with no seeded `lookup_document_type` row is a silent trap.** `src/lib/import/classify-prompts.ts` offers that array to Haiku as the valid classification vocabulary, and `scan-folder`/`ai-interpret` whitelist the model's answer against it — but `ensureDocType` then resolves the key through `typeMap`, which is built from the DB. An unseeded key passes the whitelist, misses `typeMap`, and falls through to auto-creating a type from the free-text label, so the document lands under a *generated* key. Anything matching on a literal key (e.g. `getPersonIdCardLink`, which looks for `CARTE_IDENTITATE`) then never finds it, and nothing errors. Found in Slice #23.01.Import, where six entries had drifted — one unseeded (`CARTE_IDENTITATE_ALT`) and five belonging to a different table entirely (`lookup_property_type`). **When adding a key to that array, add the migration in the same commit**, and cross-check with: `SELECT key FROM lookup_document_type ORDER BY key;` against the array. ⚠️ **Slice #23.08.Import removed the last surviving reference to `CARTE_IDENTITATE_ALT`** (it lingered in `ID_CARD_TYPE_KEYS` as a "defensive match" for two more slices after being struck from `KNOWN_TYPE_KEYS`). The lesson worth carrying: **an unseeded key cannot come back through the auto-creation path either** — `ensureDocType` generates a key from the free-text label, so it produces a *different* key, never the phantom one. A defensive match against a key nothing can emit is not defence, it is a lookalike sitting in a list of real things. Note also that `migration_021`'s three genuine alternate wordings (`AUTORIZATIE_ALT`, `CERTIFICAT_SARCINI_ALT`, `EXTRAS_CARTE_FUNCIARA_ALT`) all end in `_ALT` — the naming pattern is what made the phantom look legitimate, so match against the seed list, not against the suffix.

- **Import auto-creates document types from an AI label, with no confirmation.** Two independent code paths do it: `ensureDocType` in `bulk-import-dialog.tsx` (from the Haiku scan's `classifiedLabel`, deduped only within a single import run via `autoCreatedTypeCache`) and the extract branch of `ai-interpret/route.ts` (via `createValue`). Importing a folder of unfamiliar documents can therefore mint one `lookup_document_type` row per distinct label the model produces — a near-duplicate of an existing type ("Contract de arendă" vs "Contract de arendare") becomes a separate type, silently. Found while investigating Slice #21.10.Import; **left in place deliberately, to be fixed in its own slice** rather than folded into an investigation. Discover mode never does this. Check for drift with: `SELECT key, name, created_at FROM lookup_document_type ORDER BY created_at DESC;` — rows created long after the seeding migrations are the auto-created ones.

- **Check that a file under `src/app/admin/import/` is actually mounted before changing it.** For most of a year roughly 2,600 lines of that folder were unreachable: `/admin/import` renders **ImportWizard** (Slice #21.01.Import), not `ImportBrowser`, and nothing said so except a comment — so `import-browser.tsx` and everything only it mounted (`folder-scan-dialog.tsx`, `classify-dialog.tsx`, the three classify panels) still linted, still typechecked, and still got maintained. Slice #23.04.Import deleted all of it, so that specific trap is gone. The general one is not: the wrapper is still called `import-browser-dynamic.tsx` after a component that no longer exists, and `/admin/import` is still the only mounted entry point in the folder. Before fixing a bug there, confirm a user can actually reach the file — it is easy to spend a slice fixing code nobody runs.

  ⚠️ **Slice #23.11.search was the THIRD instance, and the pattern is now frequent enough to be a habit rather than a warning.** After `import-browser.tsx` and `/admin/import-legacy` came `complex-query-view.tsx` — 562 lines under `src/app/admin/complex-query/_components/`, imported by nothing since Slice #20.02, still linting and still type-checking, and drifted far enough that it had lost `propertyLabel` and was calling `useTranslations("complexQuery")` for a namespace that exists in neither locale file. Nothing failed, because nothing ran it. **The habit: before editing any file under `src/app/**/_components/`, grep for an import of it.** One `grep -rn "<filename>" src` answers it in a second, and "the folder is named after the screen" is not evidence — `/admin/complex-query/page.tsx` is a three-line `redirect()` and its sibling `_components/` folder looked exactly like a live screen's. Slice #23.10.dev deliberately declined to gate this file behind `<DevOnly>`, on the grounds that gating dead code implies it is live; #23.11.search deleted it instead.

- **The digit-prefix folder heuristic is gone from the wizard but ALIVE in two server-side places.** Slice #23.00.Import removed `parseFolderName` from the import wizard — a folder name starting with a digit is no longer read as `<tarla>-<parcela>-<rest>`, because it false-positived on ordinary names ("3 Calea Victoriei" → tarla "3"; "2024-Arhiva" → tarla "2024", parcela "Arhiva"). The function itself could **not** be deleted, because two consumers outside the wizard still call it and were deliberately left unchanged:
  1. **`src/app/api/documents/[id]/process/route.ts`** (steps 5–6) — the *Process* panel on a document detail page. This is a completely separate entry point from `/admin/import`, and it still has both original defects: it infers `tarlaSola`/`parcela` from a tag, and then calls **`findEntitiesByTag`** (its only caller anywhere) to associate every Document and Person in the system sharing that tag string — not just the ones from the current import. The `alreadyLinkedDocs`/`alreadyLinkedPersons` filter narrows this to entities not yet attached to *any* property, which reduces but does not remove the cross-linking risk.
  2. **`src/lib/metadata/queries.ts` → `addEntityTag`** — auto-generates `"47/2"`-style alias tags for any tag whose name passes the digit test. Now that tags link nothing this is cosmetic noise rather than a correctness problem, but it is the same guess. `tag-dialog.tsx` previews those aliases and was left calling `parseFolderName` on purpose: removing the preview while the server kept creating the aliases would make the dialog lie about what it is about to do.

  So: **do not reintroduce `parseFolderName` into the import wizard** *as a silent inference*, and treat a Process-panel bug report about wrong tarla/parcela or unexpected associations as this known gap, not a regression. Retiring it there is still its own slice — but the reason it *used* to be entangled is gone. **Slice #23.06.Import removed that coupling**: the 409 lock moved off `provenance = COORDINATE_FILE` and onto the `property_corner_source` table, so the check, the claim UPDATE, the catch-block reset and `process-panel.tsx`'s matching check no longer have to move together — they no longer exist. What remains in the Process route is only the `parseFolderName` call itself and `findEntitiesByTag`, which can now be retired on their own merits.

  ⚠️ **Slice #23.07.Import added the one sanctioned exception, and it is not a rollback of any of the above.** `PropertyStepDialog`'s create-new branch calls `parseFolderName` (via the pure `cadastralSuggestionFromFolderName` in `src/lib/import/coordinate-file.ts`) to PRE-FILL two visible, editable, Romanian-labelled tarla/parcela inputs that the user confirms before the Property is created. **The rule was never "this function is forbidden" — it is "the wizard must not decide a cadastral value alone and write it without showing anyone."** A suggestion the user sees and can correct before it is saved is a different mechanism from an inference, and it fails safely in a way the old heuristic could not: the wrong guess is on screen, next to a cursor. The suggestion is additionally stricter than the raw parser — it requires the full `<tarla>-<parcela>` shape, so the "3 Calea Victoriei" class of name yields two blank fields rather than a street address in a cadastral column. If you are here because you found `parseFolderName` imported under `src/app/admin/import/` or `src/lib/import/` and reached for the revert: check first whether the value is shown to the user before it is written. If it is, this is #23.07 working as designed.

- **A wizard-imported coordinate `.txt` arrives NOT "processed" — and until Slice #23.06.Import that produced a duplicate Property.** This entry previously claimed the opposite ("the wizard writes provenance `COORDINATE_FILE` … so opening that document afterwards shows the Process panel in its done/409 state … This is correct"). Every clause of that was wrong, and it was wrong in the most expensive direction: it described the bug as intended behaviour, so anyone hitting the bug would read this and stop investigating. Adrian found it the only way left — by noticing a flicker on the map where two identical polygons overlapped.
  **The real chain, confirmed by investigation:**
  1. `classifyFileSource()` (`src/lib/metadata/provenance-rules.ts`) maps a file by **extension only** and *deliberately never returns* `COORDINATE_FILE`. Its own comment says why: a `.txt` is indistinguishable from any other text file by name alone.
  2. `"txt"` is in `DOCUMENT_EXTENSIONS`, so `inferProvenanceForFiles` returns **`DOC_FILE`**, and that is what the wizard stamped on the imported coordinate document.
  3. `process-panel.tsx` decided done-vs-ready with `if (prov === "COORDINATE_FILE")`. `DOC_FILE` is not `COORDINATE_FILE`.
  4. The panel rendered **ready**. Pressing it built a second Property with identical coordinates, and that one populated Tarla/Parcela (the Process route calls `parseFolderName`; the wizard did not), so the two were not even equal. **That last asymmetry is closed by Slice #23.07.Import** — the wizard now SUGGESTS tarla/parcela into confirmable inputs, and applies the same `perToSlash` the Process route does, so the two paths agree on both the value and its encoding. The duplicate-Property half was already fixed by #23.06.Import.
  **Why the rule in step 1 is right and the design was still wrong:** the wizard is not guessing from a filename. `PropertyStepDialog` and `CoordinatePropertyDialog` both push the file through `POST /api/properties/parse-text` and count real corners. They had proof and threw it away, because the only channel available was a provenance code that another subsystem was entitled to infer differently.
  **The general lesson — this is the one worth carrying forward:** a display value doing duty as a lock will eventually be written by someone who only owes you the display contract. `provenance` was honest metadata to `classifyFileSource` and a mutex to the Process route, and neither was wrong on its own terms. Slice #23.06.Import gave the fact its own table (`property_corner_source`, `UNIQUE(document_id)`), so the lock is now a lock and provenance is now metadata.

## Harvested from the slice log

- **Write-if-empty, on every target a machine reading touches. Nothing a human typed is ever overwritten by a machine reading.** Read the current values first (a GET appends nothing), write only the nulls. This makes a second click, or a re-read against a document someone has since filled in, non-destructive for free. Treat a failed READ as a failed write — never as "every field is blank", which would invite exactly the overwrite the rule forbids.

- **Resolving a person from an extraction goes through the confirm-or-create ladder — never an unconditional `POST /api/people`.** The order is: exact `findNaturalPersonByCnp` → fuzzy `searchPersonsAll`, its results labelled **unconfirmed** → an explicit user decision of confirm / pick / create-new / skip. The fuzzy step tries the full name and then falls back to **surname alone**, because `person.displayName` is `"firstName lastName"` and `searchPersonsAll` is a single `ILIKE %pattern%`, so a middle name or a surname-first record misses entirely — and a missed suggestion is how a duplicate gets created. Use the shared `src/components/persons/person-resolution-dialog.tsx`; do not copy its branches into a new caller. `isCreateBranch()` is exported so a caller can render its review form under precisely the branch the dialog renders.

- **A metadata or provenance write is best-effort and must NEVER turn a successful create into an error response.** The entity row is already committed by the time `setInitialProvenance` runs, so a metadata failure that propagates would report failure for work that succeeded — or, worse, delete a correctly-created entity in a compensating action. Provenance stays outside any transaction, and its stamp goes last.

- **`src/lib/metadata/provenance.ts` is the single source of truth for provenance codes.** Never hardcode a copy of the value list in a filter dropdown or a statement map — three hardcoded copies had already drifted to values (`SCAN_OCR`, `MANUAL_ENTRY`, `EXTERNAL_DB`, `OTHER`) that were never storable, so two filters could not match a single row. Derive UI lists from the shared list so a new code cannot ship without its explanatory sentence.

- **Provenance rules (`src/lib/metadata/provenance-rules.ts`) key on the SOURCE alone, never on target × source.** The source is what determines provenance, and keying on it alone avoids combinatorial cases that all collapse to the same answer. **`unknown → null` means ASK THE USER** — `inferProvenanceForFiles` returns null for a mixed or unrecognised selection rather than picking a winner, and the UI must show a required select rather than guessing.

- **`property_corner_source` is the lock, and the `UNIQUE(document_id)` index IS the lock.** Claim with `INSERT … ON CONFLICT (document_id) DO NOTHING … RETURNING`; zero rows back means someone else already claimed it → 409. Never re-introduce a check-then-claim window, and never overload provenance (or any other display value) as a mutex again.

- **Claim the link BEFORE you PATCH the corners.** The link is the permission to write that geometry, so recording it afterwards would let a file belonging to another Property overwrite this one's corners first. Where the claim genuinely cannot happen up front — the bulk loop resolves the Property while the coordinate file is still a file handle with no `document` row to point at — take it the instant that file's Document is created, before its pages, its property link and its tags. Key the claim on whether corners were actually **written**, not on whether a file was picked: a file that was parsed and discarded did not build this Property and must stay free to build another.

- **`softDeleteProperty` must hard-delete the `property_corner_source` row.** Properties soft-delete, so the table's `ON DELETE CASCADE` never fires on the normal path and a stale link would block its source document forever. The link carries no history worth keeping.

- **`UNIQUE(document_id)` means re-pointing a link is impossible — it is not an `UPDATE`.** The recovery route is: soft-delete the wrong Property, which frees the document, then re-run the correct path. This constraint is deliberate; a request to move a link is a change of mind, not an oversight.

- **A coordinate file's NAME is a ranking signal and a warning, never a filter.** `coordinateNameConfidence(name)` returns `"strong"` (shortlisted extension **and** the name folds to a `coord` prefix) / `"weak"` (extension only) / `"none"`. `COORDINATE_FILE_EXTS` and `coordinateCandidates` stay untouched — only the parse decides usability, so a correctly-formed export with an unconventional name still imports. Exactly one `strong` candidate is pre-selected; two or more `strong` is a tie the name cannot break, so the user chooses, and every candidate stays visible and selectable either way. When the single candidate is only `weak`, show a quiet note (`role="status"`, small amber text, no banner) that blocks nothing. Derive the note from `candidates` at render time — never copy it into state, or there is a second copy to drift.

- **Apply `perToSlash` before writing `tarla` / `parcela`.** The Process route has always applied it, so suggesting a raw `"47per2"` would leave two Properties whose cadastral identifiers differ only in encoding.

- **Discover mode persists NOTHING and is safe to re-run on any document, any number of times.** No field mapping, no `customFields`, no `documentTypeId` resolution (so unlike the extract path it never auto-creates a `lookup_document_type` row), no party extraction, no `ai_interpreted_at` stamp. Do not gate its button on `aiInterpretedAt` — re-running after adding template fields to see what is still unrecognised is a primary use case.

- **`parseDiscoverPayload` never throws** — same contract as `parseTemplateFields`. A diagnostic that crashes on odd data fails exactly when the data is odd.

- **A page that cannot be sent to the model becomes a `skippedPages` entry with a per-page reason, and is reported** (including on the 422). Dropping it silently makes "the model found nothing" and "the model never saw this page" indistinguishable from outside; call the `application/octet-stream` case out by name — the file is fine, only its recorded MIME is missing.

- **`stop_reason === "max_tokens"` is surfaced as a loud TRUNCATED warning.** A silently partial read is the worst possible failure for a mode whose entire promise is completeness.

- **Cap results PER TYPE, never across types.** Four independent caps (DOC / JPERS / PPERS / PROP), with natural and judicial persons split rather than sharing a person budget — a shared budget lets one type crowd out another, which is the same defect one level down. Detect truncation with **limit + 1** (fetch 51, keep 50) and report it **per type**, so the notice names what is missing instead of saying "showing the first N results", which is true and useless.

- **Interleave the merged result set round-robin — one row per type per round, each type still ordered by code internally, types dropping out of the rotation as they run dry.** A plain code sort is why type-prefixed codes (`DOC` < `JPERS` < `PPERS` < `PROP`) put three pages of documents ahead of the first person.
