# Tailwind v4, buttons & layout

<!-- Extracted verbatim from CLAUDE.md (Slice 24.01.optimization). Original line numbers in brackets. -->

- **Buttons — always `buttonClass()`; never hand-write `disabled:opacity-*` again.** Every `<button>` takes its classes from `buttonClass({ variant, size })` in `src/lib/ui/button-styles.ts` (variants `primary` / `secondary` / `danger` / `ghost` / `bare` / `bare-danger`; sizes `xs` / `sm` / `md` / `lg`). Do not pass a `disabled` boolean — the helper emits both states and CSS picks via `:enabled`/`:disabled`, so the styling can never disagree with the `disabled={...}` prop. Layout-only extras (`ml-4`, `w-full`, `flex-1`, `gap-2`) go in `className`; anything that CONFLICTS with what the helper emits (`text-xs`, `px-4`, `rounded-full`) must come from `size` / `pill` instead — see the Tailwind stylesheet-order gotcha below. `src/__tests__/button-styles-single-source.test.ts` fails the build on a hand-written `disabled:opacity-*`. The helper is for form controls only: `:enabled`/`:disabled` never match an `<a>` or a next/link `<Link>`, so a link styled with it would render with no hover state at all.

- **Tailwind v4 has new syntax.** `@import "tailwindcss";` plus `@theme inline { ... }` instead of `tailwind.config.js`-driven theme keys. Don't reach for v3 patterns.

- **Appending a conflicting Tailwind utility does NOT override the earlier one — stylesheet order decides, not class-attribute order.** `"px-4 py-2 text-sm" + " text-xs"` does not reliably shrink the text: both `text-sm` and `text-xs` are real rules in the generated stylesheet, they have identical specificity, and the winner is whichever Tailwind emitted LAST — which is a function of Tailwind's own internal ordering, not of where you wrote them. The symptom is a class that "sometimes works", or works until an unrelated file starts using the other utility and shifts the emission order. This is why `buttonClass()` takes `size` and `pill` as OPTIONS rather than letting callers append `text-xs` or `rounded-full`, and why its `className` parameter is documented as layout-only (`ml-4`, `w-full`, `flex-1`, `gap-2` — utilities the helper never emits, so nothing can conflict). The same trap applies to any shared class-string helper: whatever the helper decides, the caller cannot un-decide by appending. Where a caller genuinely needs a different value, add it to the helper's option set. (Hit while designing the helper in Slice #23.05.UX; the four button sizes exist precisely so no call site ever needs to fight the helper for a padding or a text size.)

- **A colour set on a child element beats the parent button's hover colour — an inverting hover must force its descendants.** `buttonClass`'s `secondary` variant flips `text-cta` → `text-white` on hover, but a label rendered as `<span className="text-fade">…</span>` keeps its own colour: inheritance only applies where the child sets nothing. The button turned dark slate (#334155) while its label stayed #595F6A — a **1.63:1** contrast, unreadable — and only on hover, so it survived every static review. Found by Adrian on the "Câmpuri afișate" column pickers; seven buttons were affected across the three list views and `add-property-dialog.tsx`, all of them `secondary`. Fixed once in the helper with Tailwind v4's `**:` descendant variant (`enabled:hover:**:text-white`) rather than at the call sites, so the button owns its label colour outright and a future call site cannot reintroduce it by wrapping a label in a coloured span. The override is hover-only — at rest a muted child label is legitimate (`text-fade` on `bg-cta-pale` is 5.8:1) and the design uses it deliberately. **The general rule: any variant that CHANGES text colour on a state needs `**:` on that state; a variant whose text colour is constant does not.** That is why only `secondary` carries it — `primary` and `danger` are white throughout, `ghost` and the `bare` pair never invert.

- **A disabled `<button>` still matches `:hover`.** `disabled` stops clicks and focus, not hover styling — so `hover:bg-cta-d` repaints an inert button when the mouse crosses it, undoing whatever the disabled state was meant to communicate. Write `enabled:hover:` on any button whose hover changes colour. It also removes a variant-ordering question entirely: `:enabled:hover` and `:disabled` are mutually exclusive selectors, so neither can win over the other regardless of what order Tailwind emits them in. Every hover rule in `src/lib/ui/button-styles.ts` is written this way and a test asserts no bare `hover:` slips back in.

- **4-column grid: skip the 3-column step.** For `columns={4}` in the `Section` helper, use `"grid grid-cols-2 gap-4 md:grid-cols-4"` — do not add a `md:grid-cols-3` intermediate. At common "half-width browser" sizes (768–1023 px) the 3-column class strands the layout on 3 columns instead of 4.

## Harvested from the slice log

- **Convert every button in every file a slice touches.** Half-converting a file leaves a converted button beside an unconverted neighbour — a pale-slate `secondary` next to a plain-white one in the same table row. A leftover hand-written `bg-cta` / `border-wire` string is invisible to `src/__tests__/button-styles-single-source.test.ts` when it carries no `disabled:opacity-*`, so the test passing is not evidence a file is done.

- **The disabled visual contract, in one sentence: disabled = a white/neutral surface with a `border-wire` edge and a `text-fade` label and NO colour fill, identical for every variant; enabled = that variant's full strong colour.** Never express disabled as `disabled:opacity-*` layered on top of the enabled style — opacity MULTIPLIES the enabled appearance instead of replacing it, and 50% of "white with a grey border" is still white with a slightly greyer border.

- **Focus rings use `focus-visible:outline-*` with the existing `--color-focus` token — `outline`, not `ring`.** An outline needs no ring-offset background colour, so it renders correctly on canvas, in a white card and on dark alike.

- **Dark mode is `prefers-color-scheme` only — the app has NO dark-mode toggle,** so `dark:` resolves purely off the OS setting. `primary` lightens to `slate-400` in dark mode (the light-mode `bg-cta` #334155 is 1.69:1 on a zinc-900 page, i.e. invisible); `danger` stays red rather than inverting, because an inverted red reads as pink and stops signalling "destructive".

## Fixed widths — the window decides how many panels fit, never how wide anything is (Slice #37.12)

- **A field, a panel and the gap between them are the same width on a 1366-pixel laptop and on a 2560-pixel monitor.** A wider window fits more panels side by side, a narrower one wraps them onto the next row, and one narrower than a single panel scrolls sideways instead of squeezing it. Panels sit left-aligned beside the sidebar — a centred block moves every field whenever the window is resized, which is exactly the movement this rule removes. Adrian's decision, Field.Widths.v02 (2026-09-28), for a desktop app that has a wide screen to itself.
- **Every width comes from `src/lib/ui/field-widths.ts`, and only from there.** A handful of steps (`XS` … `XXL`, `TILE`), and each field names its step; the component applies it with `boxStyle(width)` as an inline style. `flex-1`, `w-full`, `min-w-[…]` and a grid column never decide the width of a field or a panel on a screen that has been converted — `src/__tests__/field-widths.test.ts` fails when they do (the Natural Person form and the address block today; #37.13–#37.22 add their screens to it). A width is an inline style rather than a `w-[13rem]` class so that the file stays the one place: Tailwind would need every arbitrary value spelled out literally in the source for its scanner.
- **Two kinds of field.** FIXED (dropdowns, dates, numbers, CNP, codes, phones): the box holds the longest legitimate value and is no wider, and a dropdown option longer than its box shows in full on hover (`title`). GROWING (names, places, authorities, streets, emails, notes): `<GrowingText>` (`src/components/forms/growing-text.tsx`) — fixed width, and the HEIGHT grows to show the whole value, in edit and in view mode (`field-sizing: content`, with a `scrollHeight` fallback). A growing field that holds one value never takes a line break: Enter submits as it did in the `<input>` it replaced, and a pasted line break becomes a space. Notes and the MRZ (`kind: "lines"`) keep theirs.
- **Widths are measured, not guessed.** `bash scripts/test-runner/claude.sh request measure-fields` prints, read-only, how long the archive's values really are for every field on the detail screens — the longest, the 95th percentile, how many rows each step would overflow — with the longest value masked inside Postgres so no real value is printed. The number goes in a comment beside the width.
- **The form is a whole number of panels wide** (`panelRowStyle()`: `round(down, 100% + gap, panel + gap) − gap`), so the action bar below the panels is as wide as they are and „Salvează" stays near the form it saves.
- **The labels stay where they are**: 5.5rem to the left of each box (`LABEL_STYLE`), top-aligned with its first line so a growing box does not drag its label to its middle — **except on the Natural Person (Slice #37.26, Adrian's call)**, where every label sits ABOVE its box, left-aligned, the pair exactly as wide as the box. There the rows are data — `NP_ROWS` and `ADDRESS_ROWS` in `field-widths.ts`, which the form must draw in that order (`field-widths.test.ts` reads it) — and each panel is as wide as its widest row (`NP_PANEL_STYLE`, not `PANEL_STYLE`); a `fill` box (Note, the MRZ) takes the panel's whole inner width, and a box Adrian sized by hand names its own `rem`. Its row is `npRowStyle()` (as wide as its panels, up to the window) instead of the whole-panel snap. The address block stacks only with `stacked`, so the Judicial Person and the Property keep their labels beside. Moving another screen to stacked labels is the same four steps: rows in the file, stacked helpers, panel widths from the rows, the row style.
- **The e2e check is `e2e/helpers/field-widths.ts`**: every box marked `data-width-field` and every `data-panel` must be the same pixel width at 1400 and 2400 px, and every FIXED box must hold its `sample` in the rendered font. Mark every box and panel of a converted screen, and call the helper from that screen's spec.
- **A document type's own fields are sized by rule, not one by one (Slice #37.15).** They are data, so a new type must look right with no width work: `templateFieldWidth()` in `field-widths.ts` gives text XL growing, a textarea the panel's width growing with its line breaks, a date or number a fixed M, and a dropdown the narrowest step that shows its longest option (the blank one included), capped at XXL with the full option on hover. A field whose JSON carries `width` (a step name) takes that step instead; the kind still follows from its type. Both write doors accept the key, and the Form editor carries a stored one through a save. Set it only for the field the rule gets wrong.
- **The Document's page image is a fixed panel beside the fields** (`PAGES_PANEL_STYLE`, 40rem, not narrower than the 571 px it was in a 1920-pixel window). The screen's row is whole field panels plus the page panel (`documentRowStyle()`); where one panel and the page image do not fit side by side, the page panel wraps under the fields.
- **Tables follow the same rule (Slice #37.16): the window decides how many columns are visible before the table scrolls sideways, never how wide a column is.** A list or association tab is `table-fixed` with a `<colgroup>` from `COLUMN` in `field-widths.ts` — `src/components/table/fixed-columns.tsx` gives `fixedTable(columns)`, `<FixedColumns>`, `columnHead(name)` on every `<th>`, and `TABLE_FRAME` for the frame (`w-fit max-w-full overflow-x-auto`). The table is exactly as wide as the columns it shows, so ticking a column in „Câmpuri afișate" widens it instead of squeezing the rest. A column is a step of the field scale plus the cells' padding, and one name has one width everywhere (Cod in a list, a tab and global search). `fixed` columns (codes, dates, chips, buttons) hold their value; `wraps` columns (names, titles, places) carry `WRAPS` and grow downward — so no `whitespace-nowrap` on a row. A „Câmpuri afișate" choice is stored under its old key and its old value; a stored key the build has no column for is kept and not drawn. The e2e check is `expectStableColumns` in `e2e/helpers/field-widths.ts`.
- **Every other screen follows the same rule (Slice #37.22).** The home page, the „Asociază …" screens and the administration screens sit left-aligned; a view is a `SCREEN_COLUMN` — as wide as its widest fixed piece, never narrower than a panel (`SCREEN_COLUMN_STYLE`), its paragraphs, header, status lines and alerts taken out of that width so they wrap inside it (an `sr-only` live region excepted: it is absolutely positioned, and `min-w-full` would size it by the page). A box spreads `screenBox(name)` (its step in `SCREEN`), a section card `screenPanel(name, wide?)`; the scale did not grow. `field-widths.test.ts` checks each of these views.
- **The rule is guarded everywhere (Slice #37.23).** `src/__tests__/layout-guard.test.ts` fails a component under `src/app` that centres a capped column (`mx-auto` with a `max-w-…`) and a form box under `src/app` or `src/components` whose own tag carries `w-full`, `flex-1`, `min-w-[…]` or `max-w-…`. What the rule does not reach is `LAYOUT_EXCEPTIONS` in `src/lib/ui/layout-exceptions.ts` — dialog cards, the property map, login and signup, the import wizard (FU-269), the page viewer, a few dialogs and the sidebar's quick search — each with a sentence saying why; an entry without one fails. Fix a screen or file it in the register; do not add it there to silence the guard.
- **The Natural Person sits on a width unit (Slice #37.27, Adrian's call).** `UNIT_REM` (9.25rem) and the 1rem gap: a tile of `n` units is `unitsRem(n)` — the units and the gaps between them — so a 3 beside a 3 is exactly as wide as a 4 beside a 2 and every edge falls on the same lines. Each form panel is the fewest units that hold its widest row (`NP_PANEL_UNITS`), the list tiles are `NP_LIST_UNITS` with tables that fill them (`NP_LIST_COLUMNS`, `tileTableRem`; the list tabs' `compact`), META INFO lays its sections two to a row (`compactCellRem`), and the tile row is a whole number of units (`npRowStyle`). Height is left to the content. The e2e check is `expectUnitGrid`. Other screens keep the 32rem panel until they move onto the unit the same way.
- **Three widths, one answer (Slice #37.23).** The e2e checks compare 1366, 1920 and 2560 px by default (`THREE_WIDTHS`), after `settled(page)` waits for late tiles; `expectTilesPerRow` asserts the tile row fits two, three and four small tiles at those widths, and that every small tile is exactly a panel wide.
