- Slice #21.07.Import — Provenance value set + automatic assignment. **(1)** New 7-value list (`migration_067_provenance_values.sql`): `MANUAL` / `IMAGE` / `DOC_FILE` / `COORDINATE_FILE` / `ALGORITHM` / `AI_INTERPRETED` / `EXTERNAL_FEED`. `IMAGE_UPLOAD`→`IMAGE`, `EXTERNAL_IMPORT`→`EXTERNAL_FEED`, and `TEXT_FILE` **split** by `principal_object.object_type` (PROPERTY/DOCUMENT→`COORDINATE_FILE`, PERSON→`DOC_FILE`). - Slice #23.11.search — **Global search was answering a different question than the one asked.** Adrian: "Shall we do a slice on Complex query? I don't think it's working properly anyway." Complex query has not been a screen since Slice #20.02 renamed it; `/admin/complex-query` has been a bare `redirect()` ever since. So the report was about **Administration → Operations → Global search**. **(1) The defect.** `/api/admin/metadata-query` ran three queries (person / property / document), each `.limit(200)`, concatenated them, sorted the merged array by `code.localeCompare(...)` and then took `.slice(0, 200)`. Entity codes are type-prefixed — `DOC` / `JPERS` / `PPERS` / `PROP`, 5-digit padded — and lexicographically **DOC < JPERS < PPERS < PROP**, so that last slice kept documents and silently dropped every property and every person: 200 matching documents meant the other three types were simply absent. The UI's one `resultsCapped` line said "showing the first 200 results", which reads as *there are more of this kind* and could not distinguish "more documents exist" from "your properties are not in this table at all". A message that is true and useless is worse than none, because it stops the reader looking further. Two further consequences of the same design: each sub-query truncated at 200 *before* the merge, and the cap was applied twice, so the number the UI reported was not the number of matches. **(2) Four independent caps of 50** (DOC / JPERS / PPERS / PROP) replace one shared cap of 200. Persons are split into natural and judicial rather than sharing a person budget — one shared budget would let judicial persons crowd out natural ones, the same defect one level down. Truncation is detected with **limit + 1** (fetch 51, keep 50) and reported **per type**, so the notice names what is missing: *"Se afișează primele 50 de documente și primele 50 de proprietăți — există mai multe. Restrângeți căutarea."* No COUNT — an accurate count across four filtered queries with correlated EXISTS subqueries is the expensive part of this screen, and the whole point of limit + 1 is that this slice needs no migration. **(3) Round-robin interleave.** The per-type cap alone fixes the data loss; it does not fix the experience — with a code sort, pages 1-3 would still be nothing but documents and someone searching a person's name would page four times before seeing a person. Results are merged one row per type per round, each type still ordered by code internally, types dropping out of the rotation as they run dry. **(4) Pagination at 15/page over the capped set.** At most 200 rows is one small response, so the client fetches once and slices; server-side OFFSET paging would have to materialise the same capped 200 on every request. Max 14 pages — a 15th means a cap is not being applied. Page resets to 1 on any filter change *and* on every new result set (the second is the one that matters here: unlike the entity lists, results change only when Search is pressed). **(5) Pure, unit-tested core** — `src/lib/search/interleave.ts` (`capBucket` / `interleaveByType` / `truncatedTypes` / `pageCount` / `clampPage` / `pageSlice`), 26 assertions in `src/__tests__/search-interleave.test.ts`, following the `field-diff.ts` / `coordinate-file.ts` precedent rather than leaving the logic inline in a route Jest cannot exercise. **(6) Grup / Ștampile result columns** — the group-code and stamp-code filters existed with no matching column, so a filtered result gave no indication of which group or stamp matched, or whether the filter had done anything.
