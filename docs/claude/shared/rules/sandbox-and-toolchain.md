- **Write tool truncation on `$`.** When writing files containing shell-style `${VAR}` references (e.g. docker-compose), use bash heredoc with a single-quoted delimiter (`<< 'EOF'`) instead of the Write tool.

- **The sandbox CAN run `tsc` on the whole project — it is `jest` and `next` that cannot.** `node node_modules/typescript/bin/tsc --noEmit -p tsconfig.json` completes in well under a minute and exits 0 with zero diagnostics: `tsc` is pure JavaScript, so the Windows-only native binaries are irrelevant to it. `jest` genuinely cannot run — `next/jest` needs the SWC transformer, and the Linux `@next/swc-*` binaries are not installed; Next.js then tries to download a WASM fallback from `registry.npmjs.org`, which the sandbox has no route to (`EAI_AGAIN`).

- **⚠️ But `tsc` needs the repo on a fast filesystem, and that is not always the case.** When the session reaches the repo over the remote-device bridge (Cowork's cloud mode) rather than having it locally, a full-project run is **I/O-bound on the mount, not on the CPU**: measured at 42 s wall for 4 s of user time, reading `node_modules` at roughly 1.7 MB/s, and it does not finish inside the 45 s per-command limit. Rebuilding `node_modules` in the cloud container is not a way round it either — the sandbox's npm registry allowlist blocks several of this project's packages (`zod`, `@hookform/resolvers`). **Backgrounding does not help:** the sandbox is `bwrap --die-with-parent`, so a `setsid`/`nohup` child is killed the moment the command returns, and a `pgrep -f` liveness check run afterwards matches the *new* call's own command line and reports a false "still running". Poll a result FILE, never a process name.

- **On a slow mount, run a narrowed tsconfig — it is a real type check and it fits inside the limit.** `tsconfig.json`'s `include` is `["**/*.ts", "**/*.tsx", ".next/types/**", ".next/dev/types/**", "**/*.mts"]` rooted at the repo, so the file-matching walk covers `.next/` — thousands of generated files — over the slow mount before a single line of `src/` is read. A temporary tsconfig that `extends` the real one and narrows `include` to `src/**`, `e2e/**`, `scripts/**` and root-level `*.ts`/`*.mts` (with `"exclude": [node_modules, .next]`, `"incremental": false`, `"plugins": []`, and ABSOLUTE paths plus an explicit `baseUrl`/`paths`/`typeRoots`, since a tsconfig outside the repo resolves relative paths against ITS own directory) completes in **33 s**, exit 0, zero diagnostics — a genuine full type check of every hand-written file, comfortably inside the 45 s limit. What it gives up is only `.next/types/**`, Next's generated route validator, which is a statement about the build cache rather than about the code. **Prefer this to the parser fallback whenever the slice does not add or remove an API route.**

- **⚠️ FASTEST OF ALL FOR PURE MODULES, AND IT RUNS THE TESTS: copy them into the container and drive them with a jest shim.** Do this FIRST when a slice is `src/lib/**` plus `src/__tests__/**`, and reach for the narrowed tsconfig only when the slice touches components or routes. `device_stage_files` the changed modules, their imports and their test files into the container, write a `tsconfig.harness.json` (`module: commonjs`, `outDir: out`, `rootDir: ./src`, `strict: true`, `types: []`, `paths: {"@/*": ["./src/*"]}`), run the globally-installed `tsc -p` on it, then `mkdir -p out/node_modules && ln -sfn .. out/node_modules/@` so `require("@/lib/...")` resolves, and run the emitted JS under a ~120-line `describe`/`it`/`expect` shim. Measured in Slice #26.02: **210 tests across five suites in under a second**, on a full-project `tsc` that had not finished after 15 minutes over the bridge. Type errors for `describe`/`it`/`expect`/`node:fs` are expected noise (no `@types/jest`/`@types/node` — the npm allowlist blocks both); grep them out and read what is left. **Two traps:** the shim's `it.each` must SPREAD array rows or every parameterised test fails identically, and `pkill -f "some/path"` kills the calling shell too because the pattern matches its own command line — use `pgrep -f "[s]ome/path"`. **It is not jest** — no module mocking, no snapshots, and `toEqual`'s asymmetric matchers are only as good as the shim — so say so at handover and have Adrian run the real thing.

- **Last resort, where not even the narrowed run finishes: per-file parser diagnostics.** Run TypeScript's parser over each changed file (`ts.createSourceFile(..., /* setParentNodes */ true)` and read `sourceFile.parseDiagnostics`) — it costs milliseconds per file, needs no module resolution, and catches the whole structural class, including the JSX one that is easy to write and impossible to spot by eye (`{/* comment */}` is legal between JSX children and a syntax error inside an opening tag's attribute list). **It is NOT a type check: say so plainly when handing over**, and ask Adrian to run `npx tsc --noEmit` ahead of the rest of the sequence.

**So: always run a full-project `tsc --noEmit` before handing work over, wherever the mount allows it** — it is a real type check across every file, not a filtered-for-noise approximation, and the fallbacks above exist only for the mounts where it cannot finish. Adrian still runs the full sequence on his side — `npm run e2e` (dev server running separately), then `npm run lint`, `npx tsc --noEmit` and `npx jest`; ESLint rules, actual test execution and real-browser behaviour all remain unverifiable here. A pure module can also be spot-checked behaviourally by compiling it with `tsc --module commonjs --outDir /tmp` and driving it from a small Node harness — that is how `discover-log.ts` was validated in Slice #21.10.Import without Jest.

- **`npx tsc --noEmit` type-checks Next's GENERATED route types too — and `next dev` never prunes them, so a deleted route errors for weeks afterwards.** `tsconfig.json`'s `include` carries `.next/types/**/*.ts` and `.next/dev/types/**/*.ts` alongside `**/*.ts`, so `tsc` compiles `.next/types/validator.ts` — a Next-generated file holding one `typeof import("../../src/app/…/route.js")` per API route. **`next dev` adds entries there but does not remove them when a route file is deleted.** The result is `error TS2307: Cannot find module '../../src/app/api/…/route.js'` naming a file that is *supposed* to be gone, pointing at a path under `src/` that no longer exists, in a file nobody wrote and git does not track (`.next/` is gitignored). Hit in Slice #23.06.Import: `npx tsc --noEmit` reported exactly one error, for `api/admin/import/extract-document/route.js` — a route correctly deleted by **Slice #23.04.Import**, eight commits and two slices earlier. The `.next/types/validator.ts` holding the reference was dated a week before, and 145 of its 146 route references were fine. **The tell:** the error is in `.next/`, not in `src/`, and the module it cannot find is one you meant to delete. **Fix:** `Remove-Item -Recurse -Force .next` (safe — generated, gitignored, rebuilt by `dev`/`build`), then re-run. Note that with `.next` absent the two `.next/types` globs match nothing, so `tsc` then checks your source only; to get the route-validator coverage back, run `npm run build` once — a clean build enumerates the routes that actually exist — and then `tsc` again. **The general lesson: a `tsc` error whose path starts with `.next/` is a statement about the build cache, not about the code, and the code it accuses may be innocent precisely because it was deleted correctly.**

- **Stop `npm run dev` before `npx tsc --noEmit`, for the same reason as jest.** `next dev` rewrites `.next/` continuously, and `tsc` reads `.next/types/**` as part of its input — so a run started while dev is live is compiling a tree that is being edited underneath it, on top of contending for the same disk and the couple of GB dev is holding. The symptom Adrian saw was not an error but **no output at all**; killing the dev server and re-running produced an answer immediately. Treat the whole verification sequence as: dev running only for `npm run e2e`, then stop it for `npm run lint`, `npx tsc --noEmit` and `npx jest`.

- **`npx jest` while `npm run dev` is still running → workers OOM, and it looks like a test failure.** The verification order (`npm run e2e` → `npm run lint` → `npx tsc --noEmit` → `npx jest`) *requires* a dev server for the e2e suite, so it is still holding a couple of GB when Jest starts a few seconds later in another terminal. Jest forks `cores-1` workers; the ones that lose the race die at spawn with `Out of memory: HashMap::Initialize` or `Zone Allocation failed` at a 40–80 MB heap — a **system** allocation failure, not a heap one — and are reported as `Test suite failed to run — Jest worker ran out of memory`. **The tell:** `Tests: N passed, N total` with **zero failed assertions**, and the casualties are the smallest, cheapest suites (pure-module tests importing one file) rather than the heavy ones — `help-coverage.test.ts`, which reads every `.tsx` in `src/`, passes right alongside them. Nothing about the code under test is implicated. **Fix:** stop the dev server (Ctrl+C) before `npx jest`, or run `npx jest --maxWorkers=2`. Confirm it by re-running just the failed suites — they pass in about a second. Hit in Slice #23.04.Import, where it cost a round trip diagnosing a deletion-only slice for a memory regression it could not have caused (the same full suite then ran in 4.4 s instead of 34 s with the dev server stopped, on identical code).

- **Sandbox file drift from Windows.** Occasionally the Linux sandbox shows files as deleted/added when Adrian's Windows side is clean. Don't react to it — re-run `git --no-optional-locks status` and `git --no-optional-locks diff HEAD` yourself and trust `HEAD` over the bridge's file view (`C:\dev\CLAUDE.md` → Delivering work; commit mechanics in `C:\dev\.claude\rules\git-and-commits.md`); only if the two still disagree does it go in the handover, and the pathspec commit contains the damage. The sandbox cannot run `jest`/`tsx` (Windows-only esbuild/SWC binaries in `node_modules`); whether it can run `tsc` depends on how the repo is mounted. Adrian runs the full verification sequence, both blocks — `npm run e2e` with the dev server up, then `npm run lint && npx tsc --noEmit && npx jest` with it stopped.

- **Outputs-scratchpad sync lag (Windows-tool writes → bash reads), one-directional.** When editing a large file in the temporary outputs scratchpad (e.g. a docx `document.xml` during an unpack → edit → pack cycle), edits made via the Read/Edit/Write tools can take a long time (confirmed 40+ minutes, not resolved by `sleep`/`sync` retries) to become visible to bash `cat`/`wc` on the same nominal path — bash sees a stale, truncated snapshot. The reverse direction is reliable: anything written via bash is visible to the Windows-side tools immediately. Symptom: `pack.py` (which runs in bash) reports a premature/truncated XML error even though the Windows-side `Read` tool shows the file as complete and well-formed — this is the scratchpad lag, not a real XML mistake. Workaround: pull the correct content via `Read` (in chunks if the file is long) and write it into the bash-mounted path using a bash-native command (e.g. `cat >> file << 'EOF' ... EOF`) instead of the Edit/Write tools, then re-run the bash-side step. NOTE: a similar stale/truncated read has also been seen for freshly Edit-written files under the `ga40prj` mount (e.g. `messages/*.json` showing an "Unterminated string"); when in doubt, trust the Windows-side `Read` tool, not bash, for files just edited.

- **The bridge can MOVE what it cannot delete.** Measured this session, on both connected roots: `rm` on a file the bridge itself created seconds earlier fails with `Operation not permitted`, exit 1 — and so does `rmdir` on an **empty directory** it created seconds earlier. The restriction is on the mount's `unlink`/`rmdir`; it has nothing to do with locks, ownership, or anything git did. What *is* permitted is `mkdir`, write, truncate, and **`rename` within one mount**: `mv` of a file, `mv -f` over an existing name, and `mv` of a whole directory each exit 0. **So a removal Claude is authorised to make becomes a move into a quarantine folder** — `_to_delete\` under the same connected root for anything of Adrian's (add it to `.gitignore` the first time you create one inside a repo, or it sits untracked in every `status` until he deletes it), `.git\_stranded_locks\` for the git case in the next bullet — and the handover asks him to delete that one folder. Three traps: **(1) the quarantine must be on the same mount.** `C:\dev` and `C:\dev.docs` are separate devices to the bridge (`st_dev` 38 and 39, measured) even though they are one Windows volume, so an `mv` between them degrades to copy-then-unlink; the copy succeeds, the unlink fails, exit 1, and the file is now in **both** places. **(2) `cp` then `rm` is not a way round it** — the `cp` exits 0 and the `rm` fails exactly as before, so that too doubles the file instead of moving it. **(3) Emptying a file is not removing it.** `: > file` exits 0 and leaves a 0-byte file behind, and a 0-byte `index.lock` blocks git exactly as a 786 KB one does. **This changes the mechanism, not the permission:** "deleting or overwriting anything of Adrian's outside the repo" is still on the go-ahead list in `C:\dev\CLAUDE.md` → Autonomy, and a move counts as a delete for that purpose.

- **Stale `.git` locks over the device bridge — Claude quarantines its own and carries on.** **Do:** run the fenced recipe below, with the git command inside it, every time — and hand Adrian removal line #1 if anything moved, because the quarantine is invisible to `git status` by construction and otherwise accumulates in silence. **Never:** go looking. `find .git -name '*.lock'` and moving what turns up is the one thing this rule exists to forbid — size and mtime cannot tell a live lock from a dead one, and the live one is Adrian's VS Code Source Control panel. Only what git itself named, in the output of the command that just returned, is Claude's to move.

    Why it is needed: because the bridge cannot unlink (previous bullet), every bridge-side git command that writes leaves litter, and **the *successful* commit is the dangerous one.** Measured this session in a throwaway repo on the mount: `git commit` exited 0 and stranded `.git/HEAD.lock`, `.git/next-index-<n>.lock`, `.git/objects/maintenance.lock` and a `tmp_obj_*` per object written; the **next** commit then died with `fatal: cannot lock ref 'HEAD': Unable to create '…/.git/HEAD.lock': File exists.`, exit 128. That is what stopped Slice #26.06 halfway through committing — **the commit that succeeds is the one that breaks the commit after it.** `index.lock` is *not* in a successful commit's leftovers (the commit renames it over `.git/index`); it strands from a read, or from a write that failed.

    **Quarantine only what passes all four tests. This is a filter, not a judgement, and each test is there because something real fails it:**
    1. **The line starts with `warning: `.** `error: unable to unlink '<path>'` quotes identically and names something **live** — a loose ref being deleted by `branch -d` or `update-ref -d`, or the old copy of a file being checked out. Measured: live ref deletion always comes back as `error:`, never `warning:` — which is what separates a ref git is deleting from a lock git abandoned. It does **not** make tests 2–4 belt-and-braces: a worktree source file is live *and* arrives as `warning:`, which is exactly why test 2 exists. Moving one of these destroys a branch or a source file.
    2. **The path is under `.git/`.** `unlink_or_warn` is also how git deletes **worktree** files, and those warnings pass every other test in this list. Measured at **exit 0**: `git checkout --detach HEAD~1` prints `warning: unable to unlink 'f2.txt': Operation not permitted` for every file it meant to remove, and `git apply --index` — banned by nothing, blocked by nothing — completes normally while warning about each path its deletion hunks touch. Moving one puts Adrian's source file somewhere `git status` cannot see it (this rule's own "invisible to `status`" property, turned into a hiding place) and the handover line then deletes it; where the file was `add`ed but never committed, that was the only copy. **Do not bet on the git version sparing you** — `checkout`, `revert`, `reset --hard`, `merge` and `stash` are all in this family, and the ones that currently fail earlier over the bridge (below) fail for reasons that a git upgrade could remove.
    3. **The basename is a lock or a temp**: `*.lock`, `next-index-*`, `tmp_(obj|pack|idx|rev|mtimes|bitmap)_*`, `.tmp-<pid>-pack-*`. Verified exhaustively: **no path under `.git/` ending in `.lock` is unsafe to move** — every one comes from `lockfile.c` and is either committed by `rename` (so it does not exist) or rolled back (so its content was never adopted), `objects/maintenance.lock` is a pure mutex, and a stranded `packed-refs.lock` is by definition the rollback copy of a rewrite that never landed, never the adopted one; a `gc` that stranded `HEAD.lock`, `packed-refs.lock` and four `refs/heads/*.lock` was quarantined wholesale with every ref value unchanged and `fsck` clean. The list is deliberately **narrow, not complete** — `gc.pid`, `shallow_*`, `tmp_graph_*` and `tmp_objdir-*` exist and are not matched. Anything it misses is left in place, which is the safe direction. `.git/logs/**` shows up in these warnings (`update-ref -d`, `am`) and is correctly excluded by this test.
    4. **The warning came from the command that just returned, in the same invocation.** Never from a list carried across turns: the safety argument is about *the file that existed when the warning was printed*, and `.git/index.lock` is the single most recycled path in the repo. And **never run two bridge-side git commands concurrently, in any repo** — lock warnings carry absolute paths, so a second agent's live lock can land in your capture file, pass all three greps, and be moved by an `mv` that succeeds because it is the same mount.

    **Why that is safe:** a path git named in a `warning: unable to unlink` on a command that has *already returned* was, by construction, created by a bridge-side git process that has since exited, so nothing live holds it. Checked in git's source across 2.30–2.43, not assumed: `finalize_object_file` links or renames the loose object into place **and only then** unlinks the temp, so a warned `tmp_obj_*` is already spare — the one path where it is not (`link` *and* `rename` both fail) also makes the command print `error: unable to write file`, which is the tell. A stranded `HEAD.lock` is likewise a discarded update, not a record of one: while `HEAD` is a symref the value lands by `rename` of `refs/heads/<b>.lock` and `HEAD`'s own lock is log-only, so it strands at **0 bytes**; on a **detached** `HEAD` the value does go into `HEAD.lock`, but then that lock is what gets renamed, so it only ever strands on the rollback path — measured at 41 bytes holding an OID that `HEAD` never adopted.

    Chain it onto the git command itself, from the repo top-level:
    ```bash
    top="$(git -C '<abs repo path>' rev-parse --show-toplevel)" || exit 1
    [ -n "$top" ] && cd "$top" || exit 1     # cd "" is a SUCCESS in bash — the -n test is the real guard
    o="$(mktemp)"                            # never a fixed path: two agents would share it
    { <the git command — if it is add && commit, BOTH halves here, each with its own -c flag>; } 2>"$o"; rc=$?
    #   e.g. { git -c maintenance.auto=false add src/new.ts && git -c maintenance.auto=false commit -m "feat: x" -- src/new.ts src/old.ts; } 2>"$o"; rc=$?
    cat "$o" >&2
    gd="$(git rev-parse --git-dir)" || exit 1        # --git-dir, because .git is a FILE in a worktree
    [ -n "$gd" ] && q="$gd/_stranded_locks" || exit 1 # empty would give /_stranded_locks — a different mount
    sed -n "s/^warning: unable to unlink '\(.*\)': .*$/\1/p" "$o" \
      | grep -E '(^|/)\.git/' | grep -v '/_stranded_locks/' \
      | grep -E '(^|/)(([^/]*\.lock)|(tmp_(obj|pack|idx|rev|mtimes|bitmap)_[^/]*)|(next-index-[^/]*)|(\.tmp-[0-9]+-pack-[^/]*))$' \
      | while IFS= read -r p; do mkdir -p "$q" && mv -f "$p" "$q/${p##*/}" && echo "quarantined: $p" >&2; done
    [ -d "$q" ] && echo "quarantine: $q" >&2         # the git-dir suffix the handover needs
    echo "git exit=$rc"; exit "$rc"
    ```
    **Every line of that is load-bearing, and four of them are counter-intuitive.** `cd "$(...)"` alone is *not* a guard — `cd ""` exits **0** in bash and leaves you where you were, so a mistyped repo path would put an undeletable `.git/` wherever the shell happened to be sitting, inside `src/` if that is where you were. `mktemp` rather than a fixed `/tmp/git.out` is what stops one agent quarantining another's live lock. `git rev-parse --git-dir` rather than a literal `.git` is what makes it work in a `git worktree` or a submodule, where `.git` is a **file** and `mkdir -p .git/_stranded_locks` fails with `Not a directory`. And **the braces matter**: `git add … && git commit … 2>"$o"` binds as `add && (commit 2>"$o")`, so the `add`'s warnings escape the capture entirely — measured, an `add` strands a `tmp_obj_*` of its own. `mkdir -p "$q"` sits *inside* the loop so the folder is only created when something is actually moved, which is what makes its absence mean something. Capturing **stderr only** (not `2>&1`) keeps git's block-buffered stdout from landing mid-line and breaking the `^warning:` anchor, and it is why no `PIPESTATUS` is needed; the `sed` ends `: .*$` rather than hard-coding `Operation not permitted`, because a path whose ACL yields `EACCES` prints `Permission denied` and would otherwise be dropped in silence. The `echo "quarantined:"` is what tells you whether to hand over removal line #1 at all — `mv` is silent on success, and going to look inside `.git` is the habit this rule exists to suppress. The closing `exit "$rc"` is there because the block's last command would otherwise be an `echo`, so a `commit` that died with 128 would leave the whole call at exit 0 and anything chained after it would proceed as though the commit had landed. One residual hole worth knowing: `grep -E '(^|/)\.git/'` is textual, so a warned path inside a *nested* checkout (`vendor/thing/.git/index.lock`) would be pulled into the outer repo's quarantine.

    `-c maintenance.auto=false` is not decoration either. `git commit` otherwise spawns `git maintenance run --auto` — that is what strands `objects/maintenance.lock` — and once that lock is quarantined, auto-maintenance is re-armed. Over this mount auto-gc usually dies in its pre-daemonize phase (`pack-refs`, then `reflog expire`) with `fatal: failed to run reflog`, exit 128; where that phase survives it **detaches**, so `git commit` returns 0 while a background child keeps writing to `.git` — measured: a `.git/gc.log` written 20 s after the parent returned, and a pack left without its `.idx`. `.git/gc.log` is unlinked *without* a warning, so no quarantine can ever clear it, which makes suppression the only lever. (`gc.auto=0` is **not** a substitute — measured, the lock is taken before any task dispatches. The one thing the flag also does, if `maintenance.strategy` is set, is skip the commit-graph and incremental-repack tasks; that is a fair price.)

    Measured, and this is the whole point of the slice: **three commits in a row, each with the quarantine chained on, all exit 0 — no `File exists`, no unblock line, no stop.** On the same mount without it, the second commit dies. Eleven stranded paths were cleared this way in an earlier run (six from the first commit, one from an `add`, four from the commit that failed), each moved off its own command's warning list, exit 0 every time; the commit that had been failing with exit 128 then went through immediately; `git --no-optional-locks status --short` prints nothing afterwards, because everything under `.git` is invisible to it; `git fsck` reports no missing objects; and `git count-objects -v` goes from `garbage: 3` to `garbage: 0`, because moving the temps *out* of `.git/objects/` is a net improvement. A name collision inside the quarantine (a second `HEAD.lock` from a later command) is overwritten by `mv -f`, which is correct — both are garbage — and, being a rename, it needs no unlink and succeeds.

    **A command that needs the index lock twice cannot complete over the bridge at all, and no quarantine helps it** — the quarantine runs *between* commands, and this one blocks itself. Measured on a clean board, reproducibly: `git revert --no-edit <commit>` strands `index.lock` in its first phase and dies in its second with `error: Unable to create '…/.git/index.lock': File exists.` / `fatal: revert failed`, exit 128, with nothing else running — identically on git 2.30, 2.34 and 2.43, so this is not a version the bridge will grow out of. **`cherry-pick`, `merge`, `stash` and `rebase` are the same shape.** So a `revert` goes to Adrian regardless of whether it would have applied cleanly, notwithstanding its exemption on the go-ahead list. `git commit` is **not** in this family — it takes the index lock once and the three-in-a-row result above is the proof. `git rm <path>` fails differently and just as loudly — `fatal: git rm: '<path>': Operation not permitted`, exit 128, the file untouched — so the way Claude removes a tracked file over the bridge is `git rm --cached` (index only, exempt) plus an `mv` of the file into `_to_delete\`, never `git rm`.

    **If a quarantine `mv` says `No such file or directory`, the capture you read is not the one the command just wrote** — you ran the tail of the recipe on its own, against an `$o` from an earlier invocation, because shell variables do not survive between bridge calls. That is test 4 catching you, and it is loud because the recipe has no `-e` guard. Re-run the **whole** block, git command included; do not go and find the file. A `Not a directory` is a different fault and re-running will never fix it: you are in a worktree or submodule and used a literal `.git` instead of `git rev-parse --git-dir`.

    **Everything outside the four tests goes to Adrian, and so does the lock named in `fatal: … Unable to create '<path>': File exists`** — that one was created by a command *this* one did not run. Follow the recipe and you should not see it; if you do, **first check that the command that printed your last warning list actually ran to completion** — one killed by the 45 s per-command limit strands paths it never got to warn about, and then the `File exists` lock is Claude's own after all. When you cannot tell, treat it as somebody else's and say in the handover which command you could not account for. The reason never to go looking instead: **size and mtime prove nothing** — measured, six and fourteen seconds into a genuinely running `git add` the lock was **0 bytes with an already-stale mtime**, and later in the same run it reached **786 KB**, because git writes the new index *into* the lock before renaming it over `.git/index`. A live lock looks empty and old; an abandoned one can be large. Claude cannot rule out a holder by looking either: `Get-Process` is not runnable from the bridge, and the plausible holder is Adrian's own terminal or the `git.exe` VS Code ships inside itself — **with his Source Control panel open, staging a hunk takes `index.lock` while you are reading this.**

    **There are two handover lines. They are not alternatives — hand over whichever apply, numbered, and in this order**, because #2 also removes the quarantine and running it first makes #1 report a false failure. Both carry the absolute path to the repo, because this file is loaded for every repo under `C:\dev` and a relative `.\.git` hits whichever one his prompt happens to be sitting in — **and both are written against the GIT DIR, not the repo root.** `$q` in the recipe prints a POSIX, usually *relative* path (`.git/_stranded_locks`, measured) — do not paste it. Take its git-dir portion, which is what varies: `.git` for an ordinary repo, `.git\worktrees\<name>` in a linked worktree, `<main>\.git\modules\<name>` in a submodule; flip the slashes and hang it off the Windows repo path. Getting this wrong is not a near miss: in a worktree, `<repo>\.git` is a **file**, so #2's `Get-ChildItem -Recurse` over it returns nothing and the line prints **`cleared`** while every `Remove-Item` silently missed — the false-`cleared` that the re-test exists to make impossible.
    1. **The quarantine Claude made** — hand this over only if something was actually moved. One path, unconditional, no guard: nothing live can hold a folder Claude created, so it fails *loudly* if the bridge's ACL blocks it, which — given the path came from `$q` — is the only way this one goes wrong.
       ```powershell
       Remove-Item -Recurse -Force 'C:\dev\ga40prj\.git\_stranded_locks'
       ```
    2. **A lock stranded by a command Claude never saw** — Adrian's own interrupted git, a previous session, or the `File exists` case above. Here the holder really might be alive, so this one stays the self-guarding one-liner:
       ```powershell
       $g = 'C:\dev\ga40prj\.git'; if (Get-Process git -ErrorAction SilentlyContinue) { 'git is running - let it finish, then re-run this line' } else { Remove-Item -Recurse -Force -ErrorAction SilentlyContinue "$g\index.lock", "$g\HEAD.lock", "$g\next-index-*", "$g\objects\maintenance.lock", "$g\_stranded_locks"; Get-ChildItem "$g\objects" -Recurse -Filter 'tmp_obj_*' -ErrorAction SilentlyContinue | Remove-Item -Force -ErrorAction SilentlyContinue; $left = @(Get-ChildItem "$g" -Recurse -Include '*.lock','tmp_obj_*','next-index-*' -ErrorAction SilentlyContinue); if ($left) { "NOT cleared - still there: $($left.FullName -join ', ')" } else { 'cleared' } }
       ```
       **Why that second line is shaped the way it is.** It **must re-test after the delete**: `Remove-Item -Force -ErrorAction SilentlyContinue` fails silently on a sharing violation or an ACL the bridge created, so a version that prints `cleared` unconditionally reports success when nothing was cleared — and Adrian's report back then becomes misleading evidence. It **must also delete `_stranded_locks` itself**, because its final `-Recurse` scan walks into that folder and everything in there is a lock or a temp by construction: leave it out and the line reports `NOT cleared` forever on a repo that is fine, and re-running never converges — the #26.02 unfixable-message failure, rebuilt. The `next-index-*` patterns carry **no** `.lock` suffix on purpose: this git strands them as `next-index-<n>.lock` and the wildcard matches that too, where `next-index-*.lock` would miss a bare `next-index-<n>` and then print `cleared` over it. (The scan prints `FullName` because `Name` alone would not tell him where the leftovers are.) It must stay **one** pasteable line: a pasted multi-line block runs every line before anyone reads the first one's output, so a check on one line and a delete on the next is not a guard at all. `$g` is the **git dir**, not the repo root — that is what makes it work where `<repo>\.git` is a file. A submodule's `.git\modules\<name>` is a complete git dir and one run covers it; a **linked worktree's is not** — it holds `HEAD`, `index` and `logs`, but `objects/`, `refs/` and `packed-refs` live in the main `.git` (`git rev-parse --git-common-dir`). There, hand line #2 over **twice**, once with `$g` as the worktree git dir and once as the common dir; one run alone walks neither `objects\` nor `refs\` and prints `cleared` over a stranded `refs\heads\<b>.lock` that will kill his next commit. (The recipe itself is unaffected — a warned common-dir path still matches `(^|/)\.git/` and `mv`s into the worktree's quarantine — so the gap is only ever for locks Claude did not create, which is line #2's whole job.) The `;` after `$g = '...'` is deliberate and correct — `;` is the only valid joiner after an assignment, and `&&` there parses as `$g = ('...' && if ...)`: `&&` takes only a pipeline on its right, so `if` is swallowed as a *command name* and the whole guard dies with `The term 'if' is not recognized as a name of a cmdlet, function, script file, or executable program.` — loud, but the check never runs. (The genuinely silent version of that trap is the one with a real command on the right; see `C:\dev\.claude\rules\powershell-and-windows.md`.) A `Get-Process git -ErrorAction SilentlyContinue || Remove-Item ...` chain would key off `$?` correctly — `$?` is `$false` on no match and `$true` on a match, measured — but it sprays the matched process objects into Adrian's console and hides the decision in a suppressed error record; the `if` says what it is doing. And `Get-Process git` sees only **Windows-side** git — Adrian's terminal and the `git.exe` VS Code ships inside itself (it appears under the name `git`; `Path` identifies it) — not the bridge's, which runs Linux-side against the mount. An empty result rules out a Windows holder, not every holder. That is exactly right for this line's job: a bridge-side git that was interrupted is already dead, which is what made its lock stale, so what the check is really for is the Windows holder that is merely *slow*.

    **Keep reading with `--no-optional-locks` regardless — quarantining is a recovery, not a licence to strand more.** Which reads take the lock, which of them strand it, and why the flag helps `status` but not `diff`, are in `C:\dev\.claude\rules\git-and-commits.md` → Read without taking the lock. What belongs here is what happens *under* a lock that is already present: `status`, `diff`, `log` and `show` still exit 0 (they fail to take it and silently skip the index write) while `add`, `commit`, `rm --cached`, `restore --staged` and `mv` fail with `Unable to create '.../index.lock': File exists`, exit 128 — which is why an interrupted read is the usual cause and the symptom only ever surfaces at `add`/`commit`.
